Predator · shape analysis for C

Finding memory bugs in C programs
with linked lists

Use after free, leaks, double frees and out-of-bounds writes often hide in pointer-heavy code: list traversals, error paths, kernel-style intrusive lists. Predator is a static analyser that runs inside GCC as a plug-in. It explores all executions of a program, including lists of any length, and either reports a memory error or verifies that there is none.

How it works

  1. Compile as usual. Predator is loaded into GCC with -fplugin=libsl.so and analyses GCC's intermediate code, so it understands the same C as your compiler, macros and all.
  2. Execute symbolically. Starting from main, Predator runs the program on symbolic memory graphs: heaps in which each block has a known size and each pointer a known target and offset. Unknown input, written __VERIFIER_nondet_int() below, makes it follow both branches of every condition that depends on it.
  3. Abstract unbounded lists. A loop that allocates nodes produces ever longer lists. Predator folds a chain of similar nodes into a list segment that stands for any number of them, so the analysis reaches a fixed point after a few iterations.
  4. Check every step. Each dereference, free and assignment is checked for invalid pointers, out-of-bounds offsets and blocks that just became unreachable (leaks). No error means the property holds for all runs of the program.

Each example below is a complete C program, and each shows what Predator printed on it, line for line. Lines that Predator reports are highlighted in the code, and lines that a fix changed are marked in green. The command line is shortened: the full one is in scripts/run-cases.sh.

CWE-416

The first bug almost everyone writes when freeing a linked list. create() builds a list whose length depends on input that Predator does not know (__VERIFIER_nondet_int()), so the analysis has to cover lists of every length, including the empty one.

CWE-401

CWE-131

Allocating the size of a pointer

A doubly linked list node has two pointers and an int: 24 bytes on x86-64. sizeof(n) looks almost like sizeof(*n), but it is the size of the pointer, 8 bytes. The program compiles without a warning and often runs fine, because malloc rounds small blocks up. Predator tracks the size of every block, byte by byte.

CWE-416

Freeing while iterating a Linux kernel list

System code does not use textbook lists. The Linux kernel embeds a struct list_head inside each object, links the heads into a cyclic doubly linked list, and gets from a head back to its object with container_of, that is, by subtracting the offset of the member from the pointer. Predator was designed for such code: it handles pointer arithmetic, pointers into the middle of blocks and lists that are linked through embedded structures.

#include <stddef.h>

extern int __VERIFIER_nondet_int(void);

/* a minimal copy of <linux/list.h> */
struct list_head {
    struct list_head *next, *prev;
};

#define LIST_HEAD(name) struct list_head name = { &(name), &(name) }

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

#define list_entry(ptr, type, member) container_of(ptr, type, member)

#define list_for_each_entry(pos, head, member)                          \
    for (pos = list_entry((head)->next, typeof(*pos), member);          \
         &pos->member != (head);                                        \
         pos = list_entry(pos->member.next, typeof(*pos), member))

static void list_add(struct list_head *new, struct list_head *head)
{
    struct list_head *next = head->next;
    next->prev = new;
    new->next = next;
    new->prev = head;
    head->next = new;
}

static void list_del(struct list_head *entry)
{
    entry->next->prev = entry->prev;
    entry->prev->next = entry->next;
}

/* the payload sits around the list_head, not at its start */

#include <stdlib.h>
#include <stddef.h>

extern int __VERIFIER_nondet_int(void);

/* a minimal copy of <linux/list.h> */
struct list_head {
    struct list_head *next, *prev;
};

#define LIST_HEAD(name) struct list_head name = { &(name), &(name) }

#define container_of(ptr, type, member) \
    ((type *)((char *)(ptr) - offsetof(type, member)))

#define list_entry(ptr, type, member) container_of(ptr, type, member)

#define list_for_each_entry(pos, head, member)                          \
    for (pos = list_entry((head)->next, typeof(*pos), member);          \
         &pos->member != (head);                                        \
         pos = list_entry(pos->member.next, typeof(*pos), member))

#define list_for_each_entry_safe(pos, n, head, member)                  \
    for (pos = list_entry((head)->next, typeof(*pos), member),          \
         n = list_entry(pos->member.next, typeof(*pos), member);        \
         &pos->member != (head);                                        \
         pos = n, n = list_entry(n->member.next, typeof(*n), member))

static void list_add(struct list_head *new, struct list_head *head)
{
    struct list_head *next = head->next;
    next->prev = new;
    new->next = next;
    new->prev = head;
    head->next = new;
}

static void list_del(struct list_head *entry)
{
    entry->next->prev = entry->prev;
    entry->prev->next = entry->next;
}

/* the payload sits around the list_head, not at its start */
struct device {
    int id;
    struct list_head link;
    char name[16];
};

static LIST_HEAD(devices);

int main(void)
{
    while (__VERIFIER_nondet_int()) {
        struct device *dev = malloc(sizeof *dev);
        if (!dev)
            abort();
        dev->id = 0;
        list_add(&dev->link, &devices);
    }

    struct device *dev, *tmp;
    list_for_each_entry_safe(dev, tmp, &devices, link) {
        list_del(&dev->link);
        free(dev);
    }
    return 0;
}

Why not just run Valgrind or AddressSanitizer?

Dynamic checkers are excellent, but they see only the executions you run. All of the bugs above need a particular path: a list of the right length, a malloc that fails, a parser that gives up. If no test takes that path, the bug survives. Predator checks every path symbolically, so when it reports no errors, the fix is correct for all inputs, not only for the ones in the test suite.

The price is scope. Predator analyses whole sequential programs, and its abstraction is built for linked data structures: singly, doubly and cyclic lists, lists of lists, and lists embedded in other structures. Its precision is byte-level: block sizes, field offsets, pointer arithmetic, memset and memcpy, address alignment. Predator and its successor PredatorHP have won several medals in the memory-safety categories of SV-COMP.

Want to try it on your own code? The playground runs Predator in your browser, or build it from kdudka/predator (./switch-host-gcc.sh /usr/bin/gcc), then run gcc -fplugin=sl_build/libsl.so -S -o /dev/null file.c. More details are on the project page and in the paper Byte-Precise Verification of Low-Level List Manipulation (SAS 2013). All programs from this page are in cases/.
